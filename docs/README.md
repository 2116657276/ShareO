# ShareO 文档规范

> 更新时间: 2026-07-19 | 状态: 生效

本项目同时是**产品**和**毕业设计**，文档体系为这两个目标同时服务：平时它保证工程不失控，最后它直接变成论文素材。

## 1. 文档地图

| 文档 | 职责 | 更新时机 |
|------|------|----------|
| `README.md`（根） | 快速开始、现状概览 | 大版本变化时 |
| `TASK.md`（根） | 短期任务看板 | 随手更 |
| `docs/architecture.md` | **架构唯一真相源**：组件、数据流、服务间约定 | 架构变化时同步更 |
| `docs/roadmap.md` | 里程碑与毕设时间线 | 每个 Phase 结束时核对 |
| `docs/plan.md` | 逐步开发计划（任务/选型/验收） | Phase 推进时勾选与修订 |
| `docs/standards.md` | 开发规范（分层/Go/Python/API/Git/测试/安全） | 规范变化时 |
| `docs/features.md` | 功能台账（路由/分层/文件索引） | 每个功能合入时 |
| `docs/adr/` | 架构决策记录（ADR），每个重大选型一篇 | **做选型时先写，后编码** |
| `docs/design/` | 每条主线一份设计文档 | **Phase 开工前先写，后编码** |
| `docs/eval/` | 评测集、指标定义、实验记录 | 每次实验当天记录 |
| `docs/reviews/` | 代码评审报告与修复记录（按日期归档） | 每轮评审 |

## 2. 核心规则（三条硬规矩）

1. **先 ADR 后编码**：任何影响架构的技术选型（新组件、新依赖、协议变化），先写半页 ADR 再动手。ADR 编号递增、只增不删；决策被推翻时旧 ADR 标记"已废弃"并链接新 ADR，保留决策历史。
2. **先设计后开工**：每个 Phase 开工前，按 `docs/design/TEMPLATE.md` 写设计文档并过一遍评审（和导师/AI 助手讨论均可），定稿后再写代码。
3. **实验当天记**：跑了评测就当天写进 `docs/eval/`，包含完整配置。隔周补记的实验等于没做——复现不了的数据不能进论文。

## 3. 写作约定

- 中文为主，代码标识符、文件名、API 路径用英文。
- 每篇文档头部标注 `> 更新时间: YYYY-MM-DD | 状态: ...`，日期一律用绝对日期。
- 决策类内容写"决定 + 理由"，不写探索流水账。
- 文档里引用代码用 `路径:行号` 或反引号路径，方便跳转。

## 4. 文档 → 毕业论文映射

写文档不是额外负担，是提前写论文：

| 文档 | 对应论文章节 |
|------|--------------|
| `docs/adr/` 全部 | 第 2 章 · 技术选型与论证（答辩被问"为什么不用 X"的书面答案） |
| `docs/architecture.md` + `docs/design/` | 第 3 章 · 系统设计与实现 |
| `docs/eval/` | 第 4 章 · 实验与评测 |
| `docs/roadmap.md` | 绪论 · 研究内容与工作安排 |
| `docs/features.md` + `docs/reviews/` | 功能演示与测试章节 |
